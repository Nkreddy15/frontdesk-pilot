# Decisions and implementation boundaries

| Decision | Reason and simpler option | Failure, detection and recovery | Cost impact |
|---|---|---|---|
| One TypeScript repository; API, dashboard, worker | Two founders can maintain one domain. Separate microservices add coordination without pilot value. | CI/type checks; roll back application image, keep compatible migrations. | Three small managed processes, shared database. |
| PostgreSQL owns bookings | A calendar event is not an atomic cross-channel reservation. An availability check alone cannot prevent races. | Exclusion constraints on half-open resource ranges; SQLSTATE 23P01 becomes 409 with alternatives. | Managed database and GiST index overhead; no Redis needed. |
| Short location lock plus independent exclusion | Simple pilot contention handling and predictable order; future cross-location employees require sorted resource locks. | Lock timeout is a failure, never a confirmation. Retry the same idempotency key; database still protects overlaps. | Serializes one location's short booking writes; no external calls in transaction. |
| Explicit staff and bay resource claims | Two staff cannot sell the same physical bay. Unique start time is insufficient for differing durations/buffers. | Trigger-owned projections; direct runtime writes to claims forbidden. Every appointment mutation writes an audit event. | Two resource claims per appointment. |
| 120-second holds; no renewal in first build | Keeps inventory bounded. The original plan allowed one extension; it is deliberately omitted until call timings justify it. | Expire with database time inside each scheduling transaction and maintenance; stale holds cannot confirm. | No separate hold service. |
| Reschedule original in place atomically | Original survives until the replacement is valid; no second hold that conflicts with itself. | Expected version, savepoint and transaction rollback preserve original on failure. | One transaction. |
| Chained speech with deterministic replies | Enables approved wording and confirmation gating. A speech-to-speech model may be smoother but needs stronger output guarantees and voice evaluation. | Transcription/intent/TTS timeouts, playback marks, barge-in clearing, transfer/follow-up. | Per-stage usage; real latency and cost not yet measured. |
| Luna extracts strict intent; Astra is not runtime default | Permissions, calendars, state transitions, prices and SQL are code. The model never authors executable queries or arbitrary spoken confirmation. | Zod validation, permitted catalog IDs, controller phase checks, fail closed. | Avoids large-model spend for routine actions. |
| REST Chat Completions structured output for intent | Matches the verified endpoint used by the adapter. The proposal mentioned Responses as another possible interface. | Account/model-access test required; cannot assume compatibility from model name alone. | No model calls for deterministic operations. |
| App-created Google Calendar only | Least-privilege `calendar.app.created`; primary calendars are not imported with this scope. | Dedicated mirror; polling and watch renewal; external edits create exceptions and pause new bookings. | Google quota and worker requests; no paid calendar middleware assumed. |
| Conservative external busy-event blocking | One-location pilot blocks all resources for an unmanaged event; independent overlapping external events can pause booking rather than being silently ignored. | Owner fixes events or central appointments; fresh provider recheck must resolve before unpause. | May require manual intervention; interval-union import is deferred. |
| Transactional outbox and delivery uncertainty | Messages become eligible only after commit. Exactly-once delivery cannot be promised across network timeouts without provider guarantees. | Dedup keys, leased jobs and webhook inbox; ambiguous SMS becomes UNKNOWN, never automatic resend. | One worker; no broker. |
| One worker instance during pilot | Claim serialization, leases/heartbeats and ownership checks reduce duplication; many workers are unnecessary. | Restart safely; expired calendar jobs reconcile; expired SMS jobs require provider reconciliation. Stale external writes need a follow-up sync. | Small persistent worker. |
| Supabase authentication, server-only database access | Avoid browser database keys with broad booking authority. Local access codes are development only. | RLS runtime role, signed sessions, database membership check on every request, CSRF and origin validation. | Managed auth; no custom password database. |
| No recording; explicit transcription permission | Reduces stored audio and legal exposure, but transcription/AI/SMS still need attorney review. | Keypad consent before streaming; recording setting cannot be enabled in this release. | No recording storage. |
| WASM for this environment only | Native PostgreSQL cannot start under the available user mapping; no attempt to bypass it. | Readiness and production refuse it; CI has an independent native release gate. | Free local verification, no claim of native concurrency. |
| Manual managed hosting setup first | Avoid a guessed hosting account, region, domain or paid plan. Docker images and exact service settings are supplied. | Health checks, real staging calls, signed callbacks and restore drill before cutover. | Budget from original plan; validate actual checkout pricing. |

## Scope limits that affect selling

One business/location/timezone/language per activated pilot, explicit employee and bay inventory, no variable travel time, no regulated workflow, no payment collection. Every staff member initially supports every seeded service; production provisioning must review eligibility. The owner dashboard is complete enough for the pilot workflow; staff-specific UI, self-service multi-tenant onboarding, billing and public booking forms are not implemented.

No mechanism can provide immediate conflict prevention against a Google write the system has not received. The signed pilot agreement must require central booking entry. A direct Google event is a delayed busy observation, never an authoritative booking. If that operational rule is unacceptable, do not sell a double-booking guarantee for this pilot.

No screenshot, live call quality, actual model spend, provider delivery, OAuth flow or production recovery is certified by local unit tests. See STATUS for current evidence.

## Build tooling

Development and production Next.js builds use the supported Webpack option. A cached Turbopack build panicked in this execution environment; switching to Webpack produced a successful build. No production functionality depends on a particular bundler. Local database paths are resolved after environment loading, so setup, seed and API use the same explicit data directory.

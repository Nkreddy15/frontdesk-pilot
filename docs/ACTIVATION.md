# Pilot activation — inputs and gates

The implementation needs accounts and reviewed business facts, not another generic approval to build. Supply credentials through local `.env` or the hosting secret manager, **never in chat or source control**.

If no accounts exist yet, begin with [ACCOUNT_SETUP.md](ACCOUNT_SETUP.md); source control and native CI come before paid voice or hosting activation.

## Inputs from the founders

- Real business name, public address, timezone, phone route, approved services/prices/durations/buffers, employee eligibility, hours, holidays and cancellation policy.
- A staffed transfer number with agreed hours, timeout behavior, after-hours fallback and a person responsible for leads.
- Access to a git repository and Render/managed PostgreSQL/Supabase, OpenAI API, Twilio and Google Cloud accounts. No provider account was created by this build.
- An owner-approved knowledge base, transcription/SMS consent language, retention periods, pilot agreement and qualified US attorney review.

## Twilio

Purchase or connect a suitable number in your account only after confirming the budget. Complete applicable US messaging registration and consent/opt-out configuration before SMS testing. Configure the real public API base with these application routes:

| Purpose | Application route |
|---|---|
| Incoming voice | `POST /webhooks/twilio/voice` |
| Call status | `POST /webhooks/twilio/call-status` |
| Incoming SMS/STOP | `POST /webhooks/twilio/inbound-sms` |
| Consent action | `/webhooks/twilio/consent`, generated in TwiML |
| Bidirectional media | `wss://<API>/webhooks/twilio/stream`, generated in TwiML |
| Message status | `/webhooks/twilio/messages?tenant=...&job=...`, supplied per send |
| Transfer result | `/webhooks/twilio/transfer?tenant=...&call=...`, generated by the adapter |

Configure a provider-side fallback URL/TwiML that forwards to the staffed human when the application cannot answer at all. An application fallback cannot help if the application is unreachable. Verify canonical signature URLs with the actual proxy and a real callback. Webhook handlers reject invalid signatures. Set a separate account/subaccount, spend alerts, concurrency cap and minute budget for the pilot.

The first voice prompt discloses AI and requests keypad permission to transcribe/process the call. Pressing 2, silence or unavailable service leads to a human fallback when configured. Recording is disabled, including at the application schema level. Review provider retention separately: “not recording” does not assert that every provider stores zero audio or metadata.

## OpenAI

Securely supply the API key with a project budget. Check access to the configured models: `gpt-live-transcribe`, `gpt-5.6-luna`, and `gpt-4o-mini-tts`. They were selected from official documentation; account availability and actual payload acceptance are **not yet verified**. The adapter uses realtime transcription, Chat Completions strict JSON intent extraction and PCM speech output. It never uses Astra as live audio.

Measure full end-of-speech to first audible response through a real telephone. The current implementation buffers a complete TTS response before sending audio. If this misses the latency gate, implement tested streaming TTS or change the voice architecture before accepting paying traffic. Do not describe the voice as natural merely because the text workflow passes.

## Google

Create an OAuth web application with the exact `/integrations/google/callback` HTTPS redirect URL. Configure the consent screen and required verification/publishing state. The test-mode limitations and token lifecycle must be verified in your account. Enable Calendar API and use the configured least-privilege `calendar.app.created` scope.

The owner connects through Operations. A dedicated “Frontdesk appointments” calendar is created. Existing primary calendars are not read with this scope. Require the owner to enter appointments in the dashboard. Watch callbacks plus polling discover external edits, but cannot prevent a conflicting Google write before it is observed. Direct deletions do not cancel the database appointment. The owner can request “Restore database version” or fix Google and “Recheck Google”; bookings remain paused until verified resolution, then the owner resumes in Settings.

Exercise create, move, cancel, direct Google edit, direct deletion, foreign busy event, delayed callback, expired sync token, revoked OAuth and token refresh. An uncertain calendar-creation result may leave an orphan calendar; reconcile manually instead of repeatedly pressing Connect.

## Controlled staging calls

Use synthetic customer data and a separate provider number. Set `VOICE_TEST_CALLER_ALLOWLIST` to founder E.164 numbers before enabling live voice. Enable a staging tenant's `approved_for_live` only for these controlled tests with reviewed consent. Keep SMS recipients limited to opted-in founders. Clear the allowlist only after real-pilot gates pass.

Production flags start false: `LIVE_VOICE_ENABLED`, `SMS_ENABLED`, `CALENDAR_ENABLED`. `approved_for_live` is a separate tenant gate, intentionally not editable in the routine dashboard. Release activation is an operator database action with an audit entry after evidence review. This build has not changed it for a real business.

## Before routing customer calls

Run `npm run check:readiness` with a completed private release evidence record. Confirm native concurrency, real voice evaluations, Supabase login, Google round trip, SMS delivery/STOP, human transfer, backup restore, attorney review and owner catalog approval. Retain the evidence and release commit hash. Any failed or missing item blocks rollout.
